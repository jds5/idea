# 产品设计：帮助用户选时间、选地点，并跟踪天气变化

更新日期：2026-09-30。状态：首期需求设计，部分进入内部工程，未验证市场需求。本文是定位、目标用户、功能范围与优先级的主要定义位置；本轮实际增量见[实施计划](implementation.md)，不能将完整首期能力视为已经实现。正式品牌未定，沿用 Weather App 工作名，不使用 Windy 商标或近似名称。

最新用户约束：面向欧美，先研究持续付费依赖与免费商用替代；个人开发者不能以部署超大参数模型为基础。广告、买断、会员重新评估中，下文广告权益保留为既有设计假设，尚未切换到订阅。首期规则和解释不要求 LLM；付费数据源未选定，不能把免费非商业 API 当作商业生产依赖。证据与候选见[成本研究](cost-and-free-alternatives-2026-09-30.md)，目前不因新来源存在而自动减少已定义功能的质量要求。

## 1. 用户为什么选择我们

**产品承诺：把天气预报变成一份能比较、能解释、能持续检查的出行计划。用户可以不订阅，在有需要时自愿观看广告，解锁完整规划能力。**

希望用户这样描述我们：“我能很快看出周末什么时候出门、几个地方选哪一个；预报变了能知道哪里变了。偶尔需要多地点和远期规划时，看一次广告就够我完成这次比较。”

这不是已验证的优势。竞品已有模型比较、活动时段、免费预报和广告奖励；我们竞争的是完成一个任务的总体验。首期不宣称数据独家、更准确、全球首创或完全替代 Windy 的专业能力。

| 选择理由假设 | 用户可观察的证据 | 产品必须付出的代价 | 如何证伪 |
| --- | --- | --- | --- |
| 少做功课就能决定何时出门 | 输入活动时长后，看到合适窗口、限制因素和候选替代 | 第一屏优先解释结论，不堆图层；免费可完成一个单地点任务 | 对照测试中仍比现用 App 慢、用户不能复述理由 |
| 一次比较几个地方，少来回切换 | 同一日期和个人偏好下并排比较，未知不会被当成好天气 | 所有候选使用一致统计口径；不做虚假总分排名 | 多地点比较没有改变用户选择或降低操作量 |
| 知道什么时候该重新考虑计划 | 保存时的判断与最新预报有可解释差异；支持主动提醒 | 要保存原始预测版本、处理错报；已保存的基本跟踪免费 | 变化提醒大多被认为无用或骚扰 |
| 偶尔深度规划无需订阅 | 一次明确的广告奖励覆盖完整工作区，期间不重复打断 | 收入上限较低，需要严格控制数据成本 | 用户宁愿切换免费竞品，或收入长期覆盖不了成本 |
| 对远期预测更容易形成正确预期 | 数周后显示周趋势、分歧和“暂时无法区分”，不伪造确定天气 | 愿意承认没有结论，不靠更大天数促销 | 用户仍把周趋势理解为指定日期承诺 |

## 2. 用户与市场

用户已确认：大陆以外市场、参照红色 Windy、免费竞品方向、采用广告解锁设计。其余选择是本轮规划默认。

主要用户：有时间或目的地选择余地、每周至少一次户外休闲安排的普通成人。例子包括城市周边步行、野餐、休闲骑行、周末短途旅行。需要温度、雨和风的影响解释，不愿长期支付专业天气订阅。

次要任务：提前 2–4 周比较旅行地区的大致趋势。它提供提前筛选的价值；接近出发日再用短期预报细化。它不是首期唯一获客与留存理由，因为使用频率和预测能力都有限。

初始研究样本默认来自英国英语用户，包含城市、沿海、内陆地点；这是为了控制研究和预警覆盖成本，不是已确认的英国独占发行决定。其他国家可做资料比较，正式服务国家在测试与授权后列入支持清单。界面先设计英语，中文为文档语言。

不以专业航空、远洋航海、登山安全判断、救援或商业调度作为首期目标。休闲骑行也不包含逐路段风阻、路线导航或训练指导。产品不作“适宜”之外的安全保证。

## 3. 三个核心任务

| 编号 | 触发与输入 | 输出与成功定义 | 使用频率假设 |
| --- | --- | --- | --- |
| J1 选时间 | 周末想在某地活动两小时，选择日期和偏好 | 免费得到候选窗口、主要约束和数据分歧；用户能解释为什么选它 | 每周，可带动日常查看 |
| J2 选地点 | 同一天在三个地点中选择，或比较几周后的旅行地区 | 统一标准的比较，支持“差异不足”和“信息不足”；能保存一个决定 | 每周到每月，是主要广告触发场景 |
| J3 跟踪变化 | 已经约好时间地点，临近出发再次打开 | 看到“与保存时相比”的变化，必要时重选；不为查自己的计划再次看广告 | 保存后多次回访 |

首期的活动入口只有“户外休闲”“休闲骑行”“自定义”。它们是可修改的偏好模板，不是经过气象或运动安全验证的标准。计算规则见[预报与推荐方法](forecast-method.md)。

## 4. 竞品能力如何转成我们的设计

来源为[2026-09-28 竞品调查](competitors-2026-09-28.md)；VeriSky 商店功能于 2026-09-30 再核验。不能把下表理解为这些竞品缺少一切相似功能。

| 参照 | 吸收的能力 | 首期具体取舍 |
| --- | --- | --- |
| Windy / Ventusky / Flowx | 时间轴、多来源、地图上的天气过程 | 做地点比较地图与条件解释；连续气象栅格和粒子风场在后续验证 |
| Zoom Earth | 时间和图层切换清楚、空间关系直观 | 候选地点在地图与列表联动；雷达、卫星不为视觉效果提前接入 |
| Windfinder / PredictWind / Windy.app | 从活动出发理解风和其他限制 | 保留个人偏好与时段选择；不进入航线、海况或航空专业工具 |
| Weawow / Breezy Weather | 日常免费、组件、多来源 | 日常体验完整且无强插广告；保留基础组件和手动地点 |
| VeriSky | 分歧、回看、活动窗口 | 分歧解释免费；“与保存时相比”首期必做；独立准确率榜延后 |
| Shadow Weather | 自愿广告换高级功能 | 一次奖励覆盖规划工作区；不按城市、图层、每次刷新重复收费 |

面向重度气象地图用户，Windy 仍可能是更合适的工具。第一阶段争取的是愿意把“日常查看和出行决定”交给我们的用户，而不是要求用户卸载所有天气应用。

## 5. 免费与广告解锁的功能边界

完整奖励期限、次数和异常处理只在[广告与商业设计](monetization.md)定义。下表定义功能权限，不在其他文档另建不同套餐。

| 编号 / 功能 | 永久免费层 | 规划工作区解锁后 | 优先级 |
| --- | --- | --- | --- |
| F01 地点与日常天气 | 手动搜索、可选定位、收藏、天气图标与当前预测概况、更新状态；未知条件明确呈现 | 相同数据质量 | P0 |
| F02 单地点未来天气 | 首 7 个本地日的小时视图；可用时最多 16 个本地日的逐日参考；适当降级 | 不凭解锁提高精度或制造额外天数 | P0 |
| F03 来源与分歧 | 最多三个有覆盖的模型，来源、更新时间、原生步长、分歧和缺失始终可查 | 相同透明度 | P0 |
| F04 单地点时间选择 | 首 7 天内，默认偏好下的连续活动窗口与理由 | 自定义偏好、重复调整并用于批量比较 | P0 |
| F05 地点比较 | 查看地点、基础空间位置；免费完成单地点任务 | 同一计划最多三个地点、同一时段和偏好并排比较 | P0 |
| F06 约一个月趋势 | 真实的产品说明和无真实天气混淆的示例；数据质量、范围、覆盖检查免费 | 目标日期落在未来约 30 天内的完整周趋势、候选地区比较；有数据才开放 | P0，受质量门槛约束 |
| F07 保存与变化 | 建立单地点计划；查看、删除、重命名、基本更新、变化解释不收费 | 建立完整比较方案、调整批量比较；到期保留结果快照 | P0 |
| F08 预警与服务状态 | 支持国家内的官方预警、来源链接、过期或缺失提示均免费 | 相同 | P0 |
| F09 通知 | 用户主动订阅的显著计划变化提醒；合并、去重、静默和全局限频，基本跟踪不因广告到期停用；规则见[通知规格](notifications.md) | 相同 | P0，提前至下一内部质量版核心闭环；真实通知受数据门槛约束 |
| F10 Android 组件 | 一个地点的基本天气、更新时间与计划入口 | 相同 | P1 |
| F11 分享 | 分享自己的计划摘要、生成时刻、来源和局限 | 不生成可转赠解锁码；收件人可读静态卡片 | P1 |

为了可用性和成本，规划默认最多五个活跃计划、十个收藏地点；归档的静态计划可保留或删除。达到限制时引导归档，不让广告增加名额。此限制是提案，不是已经实测的最佳参数。

P0 是闭环原型必需；P1 是公开测试前补齐。F06 若缺乏质量与许可证据，仅作为明确标注的原型示例参与研究，生产隐藏该入口及广告承诺；其他规划能力可独立验证，不能偷换奖励内容。

## 6. 端到端体验与生命周期

首次打开 → 搜索地点 → 看到日常天气和活动窗口 → 保存单地点计划 → 主动选择多个地点或周趋势 → 查看真实覆盖范围和奖励内容 → 首次试用或广告解锁 → 完成比较 → 保存结果 → 回来检查变化。

首次体验不要求注册、不自动请求定位和通知、不弹广告。定位只在用户点“使用当前位置”时申请。通知只在保存后主动启用。初版不建设云账户或跨设备同步。

长期查看频率低不是靠强推广告解决：免费日常天气、组件、保存计划和变化提醒提供回访理由。用户没有活动时不发送“你的预测待解锁”等促销推送。

## 7. 不可交换的体验要求

- 基础信息不会故意变旧、降低精度或延迟更新，以制造解锁需求。
- 分歧、未知、预警、实际来源、更新失败和历史计划是解释的一部分，不能藏在广告后。
- 只有确实可交付的功能才能出现在当前奖励说明中；远期无覆盖不能先让用户看广告。
- 同一天的差异可能无法判断；必须允许“目前没有明显更好的选择”。
- 日期、地点和用户阈值必须在结论附近可见，不能只显示一个“好天气分数”。
- 没有绑定账户不宣称绝对匿名：广告和后端仍有数据处理，详见[技术与数据边界](technical-plan.md)。

## 8. 首期明确不做

全球粒子风场、完整雷达卫星、航海航空专业图层、路线导航、分钟级降雨自研、社区照片/聊天、天气站接入、AI 聊天机器人、准确率排行榜、自动订票、订阅付费、广告积分商城、广告换气象预警、儿童定向服务、iOS 与完整 Web 客户端。配套轻量官网的建议边界见第 10 节；它不等于新增一个完整天气客户端。

“不做”是当前迭代范围，不是永久排除。后续地图应先证明能改善 J1/J2；如果目标用户坚持以全量 Windy 地图为核心，重新评估定位与成本，不在本轮悄悄扩大范围。

## 9. 成功标准与失败后的动作

核心指标是每周完成并回访的有效天气计划，不能用广告展示量代替用户价值。具体事件、研究样本、通过阈值与失败动作以[验证计划](validation.md)为准。

设计允许四种失败结论：用户不比竞品更喜欢；用户看不懂远期；广告奖励不值得等待；广告收入不足。这四项分别对应任务设计、表达方式、权益方案和商业模式调整，不用“再加一些功能”统一掩盖。

## 10. 平台与网站范围

2026-09-30 执行更新：用户在平台建议之后要求“开始规划并实现”，按 Android App 主客户端 + 轻量官网开展首个内部工程版本，完整 Web 天气应用后置。这个执行选择不等于用户已确认正式首发国家、最终品牌、收费方式或公开发布。首轮用户研究仍需要确认目标人群实际设备。

| 交付物 | 职责 | 当前边界 |
| --- | --- | --- |
| 现有 Chrome 原型 | 安装前体验核心任务、研究用户理解与选择 | 天气与广告明确模拟，先用于研究；不称为已上线产品 |
| Android App | 真实天气、选时选地、保存、变化跟踪；按既有优先级补齐通知与组件 | 集中验证留存，商业方式仍待定 |
| 轻量官网 | 产品价值、演示/截图、下载或测试入口、数据来源与局限、隐私与支持信息 | 静态页面优先，不新建登录、支付、跨端同步或完整天气查询；发布前以实际产品状态写文案 |
| 完整 Web 应用 | 桌面深度规划、跨设备使用等潜在任务 | 等真实需求证明后再设计，不为复刻 App 同步开发 |

F11 仍按静态分享卡片实现。公开可读的分享网页可在用户反馈证明图片分享不足后单独评估；需要明确用户发布意图、隐私和有效期，不能自动公开私人计划。

理由：当前核心价值既包含一次性比较，也包含保存后的回访。App 是验证通知、组件和长期使用的主要载体；官网降低了解产品的门槛。NAS/云端天气后端可以共享，但无法消除浏览器交互、存储、权限、广告权益和跨设备状态的维护工作，因此后端成本可控并不足以证明值得同步做完整双端。

Web 具备实现天气和通知的能力，不能用“浏览器做不了推送”排除它。Apple 的 Web Push 文档包含 iOS/iPadOS 主屏幕 Web App 的支持条件；Google 也有 Web 激励广告接口，但这不等于与原生广告 SDK 共用实现。[Apple 文档](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers)、[Google Web 激励广告示例](https://developers.google.com/publisher-tag/samples/display-rewarded-ad)

官网可以提供搜索和分享入口，但自然搜索流量尚未验证，不批量制造重复城市页作为获客依据。静态/预渲染页面适合先承载产品说明，完整 Web App 不是 SEO 的前提。[Google JavaScript SEO 文档](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)

推进顺序：现有原型验证任务 → 数据来源与成本验证 → 一个真实 App 闭环 → 公开测试配套官网。只有重复出现具体桌面/跨设备需求，并证明维护第二客户端值得时才启动完整 Web。若研究显示多数合格目标用户使用 iPhone，应重新评估 iOS 优先级，不默认 Web 可以等价替代 iOS，也不照旧坚持 Android。
