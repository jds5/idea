# 首个内部工程版本

日期：2026-09-30。用户已要求开始规划并实现。按上一轮建议进入 Android 主客户端 + 轻量官网；完整 Web 客户端不在本轮范围。本文记录工程增量，不替代[产品需求](product-spec.md)中的最终首期范围。

## 本轮交付边界

目标是可运行、可复现的内部版本：自托管真实天气 → 查看两个模型 → 手动选择活动时段与偏好 → 本地保存预测基线 → 刷新并检查变化。官网解释价值、实际进度、数据局限和隐私；沿用独立工作名 Dayward。

采用 Kotlin / Jetpack Compose；Node 内置 HTTP、文件和测试模块组成小型网关与采集任务。地点先用有限欧美城市清单，避免假装已实现全球地理搜索。Android 不要求注册、定位或广告权限；不新增 LLM、付费数据或支付依赖。

当前 Open-Meteo 自托管返回拼接时间序列，不能仅靠抓取时间确认每点起报周期及原生分辨率。保留 `runAt=null`、`nativeHourly=false` 和原因；实况字段不伪造。可查看天气和保存手选时段，自动“符合偏好”推荐保持关闭。领域引擎为将来可追溯数据实现完整门槛，以测试数据验证不等于实测气象质量。官方预警尚未接入，明确显示未知。

## 工程结构

- `service/`：来源归一化、质量门槛、窗口评价、缓存网关、后台采集和测试。
- `app/android/`：Compose 客户端，地点/天气、活动时段、设备内计划与手动复查。
- `website/`：静态配套官网，不承载第二套天气客户端。
- `compose.yaml`：本地按需来源、采集任务、持久缓存和网关。采集失败不删除上一次有效结果；网关独立读取缓存，家庭来源不在用户请求链路上。

本地共享卷仅用于验证 NAS 任务与云网关的逻辑分工。本轮不声称跨公网复制、Cloudflare、家庭网络或 N301 性能已部署验证；真实分机发布与鉴权留到下一增量。

## 顺序与验收

1. 来源归一化与规则：缺失不补零、两独立模型、起报/原生小时/新鲜度门槛、过去时段和时间连续性测试。
2. 网关与采集：固定地点、输入校验、原子写入、错误/过期状态；真实自托管请求验证，服务重启保留结果。
3. Android：编译、单元测试和 lint；保存完整基线，重新查看时比较同一时段与口径。真实设备、TalkBack、动画、后台限制单列待验，不把编译当作真机验收。
4. 轻量官网：桌面/手机浏览器检查；不虚构商店链接、用户评价或已上线能力。

## 后续增量

首先解决模型逐点版本和原生时间步溯源，再开放自动候选窗口。随后补齐多地点比较、官方预警、七天覆盖质量验证；通知、组件、分享是公开测试前工作。周趋势继续受质量与基准门槛约束。真实广告、会员、买断仍待商业决策，本轮无收费或模拟广告混入真实客户端。
