# Windy 与约一个月天气预报：数据源调研

核验日期：2026-09-28。阶段：研究；包含小型公开接口实验，不代表应用开发或准确率验收。供应商能力、价格和许可按本次官方页面记录，采购前需再次确认。

后续范围更新：用户已确认参照红色 Windy.com、不服务大陆地区，并先调查免费竞品。下文保留初次数据源调研时的建议与确认状态；其中“产品身份未确认”和中国市场路线不再代表当前范围。最新要求见[产品首页](../README.md)，竞争格局见[海外竞品调查](competitors-2026-09-28.md)。

## 1. 结论与建议

实现约一个月的天气趋势在数据获取上可行，无须先自研全球天气模型。但应分别处理未来几天的天气详情与第 3–6 周的趋势、概率和不确定性。

本轮推荐（规划建议，未确认采购）：

1. **全球原型：Open-Meteo 短期 Forecast API + Seasonal API 中的 ECMWF EC46。** 已完成无密钥实测；代码、响应和边界见[实验记录](../experiments/README.md)。正式商业接入需要核实覆盖 Seasonal 的套餐。
2. **中国用户：短期服务比较彩云、和风；长时效重点评估彩云 40 天次季节与 EC46。** 彩云需企业授权；和风 30 天旧版存在迁移风险，不宜直接锁定为唯一长期来源。
3. **自主数据管道：将 ECMWF 直接数据、NOAA GEFS 列为后续候选。** 适合需要全球格点地图、批量分发或成本规模化时评估；初期先证明用户需要和数据质量。

尚未证实“Windy 当前能做 30 天逐日预报”这个前提。未找到证据不等于该功能绝不存在；仍需具体 App、版本或页面确认。用户尚未确认红色 Windy.com 或蓝色 Windy.app，本轮分别核查，主要按 Windy.com 研究。

## 2. Windy 的数据究竟来自哪里

### 两款产品必须分开

| 产品 | 本次能确认的事实 | 对开发的意义 |
| --- | --- | --- |
| Windy.com / Windyty | 2024 年官方公告推出 ECMWF/AIFS 15 天扩展；当前多模型页面仍有 15 天入口 | 可作为多模型、地图和趋势交互参照，不能据此称其支持一个月 |
| Windy.app | 官方模型说明列出 ECMWF、GFS 等，多个全球产品为 10 天；也有更短的区域模式 | 同名不代表相同公司、接口或模型产品 |

来源：[Windy 15 天官方公告](https://community.windy.com/topic/34378/windy-launches-premium-15-day-forecast-for-ecmwf-model-using-aifs-technology)、[当前比较页面](https://www.windy.com/multimodel/47.591/19.230)、[Windy.app 模型说明](https://windy.app/support/windy-app-weather-forecast-models.html)。公告评论解释了当时 IFS 前 10 天加 AIFS 后 5 天的方式；这是发布时实现，不能推定所有当前版本仍完全相同。地图时间轴与单点预报表的时效也可能不同。

Windy.com 主要把 ECMWF、NOAA GFS、DWD ICON 等机构的天气模式输出加工为可查询、可比较的产品。得到相同上游模型，是实现类似用途的起点；要达到相近体验，还涉及更新调度、地形处理、地图渲染、缓存及误差表达。不能把它理解成手机独立计算全球天气。

官方旧论坛有“没有 15–30 天”的历史答复，但后来已有 15 天产品，所以旧答复不能当作今天的完整规格；也不能把旧帖中“任何模型都没有长预报”的说法扩展成科学结论。[旧答复，仅用于历史对照](https://community.windy.com/topic/24107/more-days-forecast-in-advance)

### Windy 官方 API 不等于购买 App Premium

- **Point Forecast**：结构化单点数据，`POST https://api.windy.com/api/point-forecast/v2`。当前文档模型表未列 ECMWF；价格页明确排除 ECMWF。Professional 标价 €990/年、10,000 请求/日，可协商扩容。免费 Testing 返回经过打乱、轻微修改的数据，只适合开发联调，不可用于天气或准确率验证。[接口](https://api.windy.com/point-forecast/docs)、[套餐](https://api.windy.com/point-forecast/pricing)
- **Map Forecast**：基于 JavaScript/Leaflet 的地图服务，可嵌入页面和移动设备。当前价格页 €990/年，ECMWF 另列 €1,000 选项，且标注仅内部使用；不能据此假设可向公众发布含 ECMWF 的消费 App。[地图文档](https://api.windy.com/map-forecast/docs)、[套餐](https://api.windy.com/map-forecast/pricing)

本轮未购买或登录测试这些服务。ECMWF 上游数据政策已开放，不自动改变 Windy 自身服务合同或已公布的产品限制。若选择 Windy 地图，需要另行确认公众移动端展示、品牌、缓存、模型和时效范围。

## 3. 一个月预报如何产生，能表达什么

### 从观测到集合预报

典型链条是：气象站、卫星、探空等观测进入分析系统，形成起始的大气状态；数值模型或经过训练的天气模型向未来推进；集合系统使用一组不同的初始条件或扰动，得到多条可能轨迹；随后经过统计处理、格点到位置的提取，变成温度、降水和风的产品。应用开发通常接入后两层，不负责全球观测同化和超级计算。

远期预测仍有依据：海洋、陆面等变化较慢的状态可以影响后续大气；因此可能对一段时间偏暖、偏冷、偏湿有预测能力。ECMWF 的次季节产品覆盖 46 天、每日更新、约 36 km，主要解释逐周平均及相对于模式气候的偏差。[ECMWF 次季节说明](https://www.ecmwf.int/en/forecasts/about-our-forecasts/sub-seasonal-range-forecasts)

这里的“预测能力”随地区、季节、变量和预报提前量改变，不存在一个对所有城市都适用的“30 天准确率”。温度趋势、周降水异常和某一天某一小时下雨，是不同难度的问题。

### 产品层的建议

| 提前量 | 建议呈现 | 需要避免的表达 |
| --- | --- | --- |
| 0–2 小时 | 若有短临源，展示降水临近变化与官方预警 | 用长时效模式推断几分钟后是否下雨 |
| 1–7 天 | 逐小时/逐日天气、降水概率、风与阵风 | 只给无来源图标，隐藏更新状态 |
| 8–15/16 天 | 趋势及集合区间，可附逐日参考 | 把跨模型分歧隐藏为一个确定答案 |
| 16–30/46 天 | 周趋势、距平、经过验证的概率、范围 | 宣称某街道某日几点一定下雨 |

这张表是设计建议，不是固定的科学可靠性阈值。远期仍可有日历视图，但应标记远期趋势，支持切换周汇总，避免视觉上与明天的确定性相同。

“距平”指预报相对于匹配的历史基准偏差。可以显示“这一周更可能偏暖”；不能把格点的单条远期轨迹变成没有不确定性的逐日天气承诺。若用集合成员自算概率，要说明阈值、有效成员数量，并校准和检验；“成员中 70% 发生”不自动等于真实世界已校准的 70% 概率。

不能用“集合平均每天都有少量雨”推出“每天都会下小雨”：不同成员的雨可能发生在不同日期。也不能把 6 小时间隔插值成 1 小时，宣传为新增小时级预测能力。

## 4. 数据源比较与获取入口

### A. Open-Meteo：最适合先验证产品

[普通预报](https://open-meteo.com/en/docs) 最多请求 16 天；[Seasonal API](https://open-meteo.com/en/docs/seasonal-forecast-api) 可选 EC46 或 SEAS5。前者解决次季节趋势，后者覆盖更长季节尺度，本轮无需把产品扩展到半年。

EC46 接口的重要差别：日/小时成员产品提供 51 条轨迹；周统计使用更大的上游集合。约 36 km、原生 6 小时，数据未做局地偏差校正。不要把 API 选点能力等同于街道级准确率，也不要把无后缀字段直接当集合均值。具体请求与实际成员数见[本地实验](../experiments/README.md)。

**商业边界**：免费托管 API 用于非商业；当前价格矩阵将 Seasonal、Ensemble 等列在 Professional 及以上，Standard 不含这一组产品。免费限额包括 10,000 次/日，长时段、多变量等请求可能折算为多次。数据 CC BY 4.0、服务器代码 AGPLv3、托管服务使用条件分别适用。本次页面未核得可靠的固定月价数字，不沿用旧博客价格。[价格与套餐](https://open-meteo.com/en/pricing)、[条款](https://open-meteo.com/en/terms)

建议：先以公开接口做非商业技术验证，再决定购买 Professional 或改用直接来源。只有 30 天日历不要求下载全球数据。

### B. ECMWF 直接数据：更自主，但接入更重

ECMWF 已于 2025-10-01 完成实时目录 CC BY 4.0 开放，取消信息数据费；定制交付、服务等仍可能收费。不能继续照搬“ECMWF 数据一律昂贵、不可商用”的旧结论，也不能误读为所有文件在任何访问方式下都免费。[开放路线图当前状态](https://www.ecmwf.int/node/29013)

公开子集入口为 [Open Data](https://www.ecmwf.int/en/forecasts/datasets/open-data)、[数据目录](https://data.ecmwf.int/)，有 AWS/Azure/GCP 副本和官方 `ecmwf-opendata` 客户端。常见公开格点为 0.25°、GRIB2；它与 Windy 标示的 9 km 原生模型产品并非必然相同。更高分辨率或更完整产品应查交付目录和服务协议。

**不要假设普通中期下载脚本把 `step` 改到 1104 小时，就能取得 EC46。** 必须核对具体 stream、产品、变量、成员、步长和账号权限。本轮未完成实时 EC46 原始 GRIB 交付验证。可从 [Access to forecasts](https://www.ecmwf.int/en/forecasts/accessing-forecasts) 进入实时产品目录；向供应商核实所需周统计或成员场的可交付方式。

研发归档另有 S2S，但它与业务实时交付不同：当前官方 FAQ 说明依模型延迟 48 小时或 1 周，且 2026-05 已迁移到 ECDS/CDS-API。旧文常写的统一“延迟三周”已不能照搬；不同成员中心还存在 CC BY 与 CC BY-NC 许可差异。[S2S FAQ](https://confluence.ecmwf.int/spaces/S2S/pages/40796925/FAQ)、[S2S 当前许可](https://ecds.ecmwf.int/licences/s2s-licence)

### C. NOAA：GEFS 是一个月方向，GFS 不是

| 数据 | 可参考时效 | 用途与入口 |
| --- | --- | --- |
| GFS | 最长约 16 天 | 中期确定性预报、风场；[NOAA 数据说明](https://www.ncei.noaa.gov/products/weather-climate-models/global-forecast) |
| GEFS | 官方 v12 说明中 00 UTC 可到 35 天，其他周期通常 16 天；31 成员 | 独立的集合对照；[模型说明](https://www.emc.ncep.noaa.gov/emc/pages/numerical_forecast_systems/gefs.php)、[产品和文件索引](https://www.nco.ncep.noaa.gov/pmb/products/gens/) |
| CFSv2 | 有更长期气候产品 | 可研究季节背景，初版非必需；[官方数据入口](https://cfs.ncep.noaa.gov/cfsv2/downloads.html) |

注意 GFS 下载页的“最近 30 天归档窗口”不是“未来 30 天预报”。GEFS 也要选择真的含第 17–35 天的文件集，不能从只到 384 小时的子集推断完整覆盖。本轮核对了官方说明，未下载和解析 NOAA GRIB，也未对其目标地区质量排序。

### D. 彩云：国内长时效的明确商业候选

彩云公开了 [v3 40 天次季节预报](https://docs.caiyunapp.com/weather-api/v3/meteorology/subseasonal.html)，端点为 `https://singer.caiyunhub.com/v3/subseasonal`，需要 token，属于企业套餐增值服务。文档明确提醒数据为粗空间分辨率的大尺度预报，前 15 天建议用常规逐日接口。

它是本轮找到的国内可直接讨论采购的长时效候选。但公开页没有充分说明上游模型、完整分辨率、校准和检验结果，不能猜成“确定使用 ECMWF”或“必然比海外接口准”。请求参数、数值单位、模型起报时间及例子中的异常数值应在试用时核实；未用文档示例作真实天气。

[常规逐日文档](https://docs.caiyunapp.com/weather-api/v2/v2.6/4-daily.html) 提供未来约 15 天，受套餐控制，和 40 天接口是不同产品。公开企业价格未确认，需报价。缓存、对外衍生展示与数据再分发权限应按具体合同明确；通用协议不能代替企业采购条款。[平台协议](https://platform.caiyunapp.com/user/user_agreement/)

### E. 和风：30 天旧接口存在，但有迁移风险

[旧版 `/v7/weather/{days}`](https://dev.qweather.com/en/docs/api/weather/weather-daily-forecast-webapi-v7/) 支持 `30d`，当前页面同时标记将弃用。[推荐的 v1 Daily](https://dev.qweather.com/en/docs/api/weather/weather-daily-forecast/) 则为 `GET /weather/v1/daily/{latitude}/{longitude}`，`days` 当前范围 1–10。

因此需要向和风确认：旧 30 天能否为新项目开通、服务截止时间、替代产品及长期授权。不能仅看搜索摘要就承诺新 API 支持 30 天。可作为常规天气候选，长时效供应不能只押在旧版本上。

当前通用天气价格组示例：每月前 50,000 请求免费，后 950,000 次每次 ¥0.0007；100 万次约 ¥665。这只演示官方价格组算法，不代表 30 天产品已获开通或单次刷新只需一个调用。需确认实际 SKU、账户权限和地区。[计费说明](https://dev.qweather.com/en/docs/finance/pricing/)

### F. OpenWeather：现成 30 天，但先验证语义

[Climatic forecast 30 days](https://openweathermap.org/api/forecast30) 的端点为 `https://pro.openweathermap.org/data/2.5/forecast/climate`，支持经纬度、密钥与 1–30 天。名称本身标示气候预报；不能把它等同于普通短期逐日 API。模型来源、长期校准表现和适用套餐需要进一步确认，本轮没有有效商业密钥实测，作为备选，不作为首选依据。

## 5. 本轮真实实验说明了什么

在本机 Docker 中使用现有 `python:3.11-slim`，4 组公开 GET 均返回 HTTP 200。北京短期 16 天全部有值；北京和柏林 EC46 请求均返回 46 个日期，实际每序列 45 天非空；北京周趋势 7 个日期标签，实际 6 周非空。原始响应和逐字段覆盖已保存。

这证明：可取得足够覆盖“一个月”功能的数据，无须先采购 Windy；也证明：生产应用需要处理格点偏移、末端空值、集合成员和产品切换。

没有证明：30 天逐日天气准确、Windy 使用相同处理算法、供应商达到生产 SLA、商业端点可用、Android 体验达标。没有伪造准确率或把生成数据当观测。[复现和限制](../experiments/README.md)

## 6. 建议的最小技术方案

下面是工程建议，不是已启动的实现：

```text
Android / 其他客户端
        ↓ 单点预报、周趋势、来源和更新时间
自己的轻量后端：鉴权、配额、缓存、统一单位、错误和缺失状态
        ├─ 短期供应商：逐小时 / 逐日
        ├─ 次季节供应商：周距平 / 集合区间
        └─ 若首期需要：单独的官方预警或授权预警源
```

每份数据保存 `provider`、`model`、`model_run_time`（上游提供时）、`retrieved_at`、`valid_time`、时区、原始网格、单位、统计区间、许可和缺失标记。没有起报元数据时明确未知，不用抓取时间替代。缓存按模型周期和供应商条款更新，不让每次打开 App 都拉 51 个成员。

在后端保留模型来源分界，短期与远期交接不能静默平滑成同一置信度。展示长期分位数前先定义是日最高温的成员分布、周均温的分布还是其他统计对象。

若目标包含 Windy 风场地图，需另立数据与渲染验证：点查询 API 不能经济地逐像素请求整张地图。通常需要区域格点场、空间切片、按时次版本化的瓦片/向量场、CDN 和客户端粒子渲染；短临雷达、卫星、预警又是不同数据产品。先只做一个区域、一种风场、少数时次验证流畅度与带宽，再考虑全球。

Docker 适合隔离下载器、GRIB 解码（如 ecCodes）、统计作业和 API 服务；容器环境本身不会产生更准预报。OpenCLI 适合官方文档/社区调研和观察公开界面；正式数据获取应走授权 API 或数据文件，避免把浏览器抓取当长期生产接口。

自建可研究 [Open-Meteo 官方仓库](https://github.com/open-meteo/open-meteo) 的下载与服务实现，但需要承担数据导入、存储、持续更新、故障恢复和相应代码许可义务。初期不建议因已有 Docker 就直接部署全量全球系统。

## 7. 成本应怎样估算

建议先区分四笔：模型/数据授权及交付、托管 API、自己的缓存/存储/出口、地图瓦片与 CDN。

一个纯示例：10,000 DAU，每天打开 3 次，每次 2 个逻辑请求，30 天为 180 万请求；若按地点和时次复用达到 90% 命中，则约 18 万次上游请求。命中率只是计算假设，用户位置分散、参数、实时更新和合同缓存限制都会改变结果。Open-Meteo 还需乘上相应长时段/变量计费权重。

不能把“每次 HTTP 请求”统一当成所有供应商的一次计费；也不能把 Windy 地图 session、点预报 request、原始 GRIB 下载字节混为一谈。先统计实际请求形态，再询价，而不是先购买年度套餐。

## 8. 如何验证它值得做

下一阶段先做数据评估，不要求先写完整 App：

1. 选目标用户任务与城市/地形样本。例如通勤关心短临雨，旅行关心日期窗口，户外运动关心阵风和局地地形；评价指标应不同。
2. 固定请求参数，保存当时发布的预报快照、起报时间和有效时间，留住失败与空值。不要用后来更新的预测冒充“一个月前看到的预测”。
3. 短期温度评估 MAE/偏差，降雨事件检验概率与发生结果；集合可用 CRPS，概率事件可用 Brier 分数和可靠性图。长期重点按第 3、4、5、6 周、区域和季节对比周统计，与同季节气候基准比较。[ECMWF 概率检验说明](https://confluence.ecmwf.int/spaces/WLS/pages/394992254/Verification)
4. 使用可合法获取的站点观测作主要参照，并解释站点高度与网格代表性；再分析可辅助，但不能混称现场观测。偏差订正训练与验证按时间隔离。
5. 先连续采样 6–8 周发现更新、缺失和稳定性问题；可靠的远期质量结论还需跨季节历史回报/独立样本。一次 30 天命中、几张截图和单次调用都不足以证明准确率优势。

建议的进入实现条件：目标区域的可用率与有效覆盖满足事先约定要求；长期产品相对气候基准有可解释的技巧；单位用户成本可接受；商业展示、缓存和归档权利明确。具体阈值须按用户任务制定，目前没有已验证结果。
