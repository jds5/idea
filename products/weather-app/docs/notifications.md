# 计划变化通知规格

更新日期：2026-09-30。用户已确认：希望计划时段天气发生变化时主动提醒，且谨慎控制打扰。以下参数、技术选型和默认行为为整改设计，尚未实现，也不是用户已逐项确认的设置。本文件是通知频率、静默、触发和去重的唯一主要定义位置。

## 用户得到什么

通知回答“已保存的这次活动需要重新看一下吗”，不承担每日天气播报、广告召回或严重天气报警。基本计划跟踪免费，与未来广告/会员是否到期无关。官方预警继续单独设计，不能把计划提醒包装成安全保障。

保存成功页提供“有明显变化时提醒我”说明和主动开启入口，默认不选中；授权后逐计划记录是否开启。拒绝权限仍能保存、手动复查和读变化详情，不反复弹权限请求。计划详情随时可以暂停，设置中可以全局停用并打开系统渠道设置。

Android 13+ 通知需要运行时权限；应在用户明确启用提醒时请求，而非首次打开 App 时申请。[Android 通知权限文档，2026-09-30 核验](https://developer.android.com/develop/ui/compose/notifications/notification-permission)

## 默认节奏与打扰预算

| 项目 | 规划默认 |
| --- | --- |
| 跟踪范围 | 已开启提醒、尚未开始、距离开始不超过 48 小时的计划；较远计划显示“临近再开始跟踪” |
| 后台检查 | 有活跃跟踪时，目标每 3 小时检查一次网关缓存；不是每 3 小时通知，也不是每次直连天气上游。没有活跃计划则取消相应周期任务；远期计划仅安排进入跟踪范围后的检查 |
| 普通通知总上限 | **全 App 滚动 24 小时最多 1 次**，不是每个计划各 1 次；多个待提醒计划合并，未变化不发 |
| 静默时段 | 设备当地时间 22:00–08:00，允许用户调整；不按旅行目的地时间打扰睡眠。目的地时间只负责显示活动时段 |
| 默认渠道 | `Plan changes`，`IMPORTANCE_LOW`，默认无声音/振动/悬浮打断，遵守用户系统设置；不创建新渠道绕过静音 |
| 最后时限 | 发送前再次确认活动尚未开始；开始后不发迟到的计划调整提醒、不补发过期队列。后台只保留检查记录供查看 |
| 静默/限频期间 | 合并当前有效事件，解禁后重新拉取并判定；如果恢复原状态或活动已开始则丢弃，不按旧队列逐条补发 |
| 不发送 | 单纯更新成功、无变化、微小数值抖动、权限拒绝、后台网络失败、购买/广告到期、活动即将到来、首次保存、周趋势切换产品 |

“周趋势进入逐日范围”保留为 App 内说明，不单独推送。这替代早期文档中按每计划当地日期限频、切换预报范围也提醒的默认方案，防止多计划和跨午夜造成打扰。

无声通知是默认取舍：降低打扰，也可能降低被注意的程度，有限测试中需观察是否错过有用信息；用户可通过系统渠道调整。Android 渠道的重要性和声音最终由用户控制，App 不能修改已创建渠道的这些行为来绕过选择。[Android 通知渠道文档，2026-09-30 核验](https://developer.android.com/develop/ui/compose/notifications/channels)

## 变化判定与数据门槛

分别保存“原始基线”“最新有效检查”“上次已通知的状态”。原始基线不被后台检查重写；详情继续与保存时比较，主动通知则要相对上次已通知状态抑制重复。

1. **可比较**：同一计划修订、地点及可比网格、绝对时间区间、模型/产品、变量定义、单位、变换版本和偏好。替换来源或修改计划要重新建跟踪基线，不报成天气变化。旧快照不能推进检查版本。
2. **确有新预报**：取得可追溯的新起报版本且输入新鲜、必要变量完整；同一版本重复抓取不能再次确认变化。抓取时间不替代起报时间，内容指纹只能做重复检测。拼接序列需追溯所比较小时的实际版本，不能仅拿整个响应的时间标签。
3. **有决策意义**：比较逐小时超出用户温度、雨量、风和阵风偏好的时段，而非只看窗口总量。跨越偏好阈值、超阈时段进入/离开活动窗口，或其开始/结束移动至少一个原生小时，可生成候选；无任何阈值/时段影响的数值变化只放详情。微小边界抖动仍需通过以下防抖，不由格式化字符串判断事件。
4. **防抖**：暂保留连续两个不同新起报周期出现同方向影响的保守规则；中途恢复就撤销候选。数值变化但影响时段/因素相同，更新同一事件而非创建新提醒。恢复类事件仅在此前恶化确实通知过、且恢复也通过确认时进入通知队列，避免“从没听说变差却通知变好”。
5. **不足与分歧**：缺值、过期、来源变更、预警未知属于信息状态，不能写成天气恶化。新数据表明模型对某个阈值有分歧时可以解释“预报对风的判断发生分歧”，不能把模型票数当概率。

窗口建议的 `fits/mixed/outside/insufficient` 同时受预警等因素约束，因此不应作为唯一通知信号。未来可在小时输入及版本已核验时，提供事实性的“预报参考有变化”提醒，即使官方预警尚未接入；这不等于恢复自动推荐，也不能说“现在安全”。此层分离是规划方案，必须先有独立的比较资格判定和测试。

**当前真实数据的阻断项**：适配器 `runAt=null`、原生步长未核验，不能满足上述确认规则。下一版应先补溯源或更换已验证的适配方式；机制可以用明确标注的测试快照验收，真实订阅入口必须解释暂不可用，不能显示“已保护你的计划”。纯抓取次数或点击“测试通知”不算真实天气变化验证。

两个新起报周期确认可能使通知延迟数小时乃至错过活动，这是一项尚待验证的产品取舍。记录从首次候选到确认的时长和未及时提醒比例；若过于迟缓，再单独评估按事件影响程度调整确认要求，不能在实现中悄悄换成两次 HTTP 请求。此版本不承诺发现所有突发变化。

## 通知内容与返回路径

单计划示例（文案示例，非当前真实预报）：

> Your Saturday walk forecast changed
>
> London · Sat 10:00–12:00. Rain is now forecast during your saved window. Review the change.

默认锁屏公开版本只写“一个已保存计划的预报有变化”，隐藏活动名、目的地和具体时间；展开内容遵循系统隐私设置。点击直接进入对应计划的前后比较，不跳首页、不要求看广告。操作提供“查看变化”“暂停此计划提醒”；合并通知进入变化列表。计划已删除时进入已保存页并说明，不崩溃。

## Android 与持久化方案

本地测试阶段采用 **WorkManager + 本地通知**：使用已有网关缓存，避免为了试通知先引入账号、推送 token、FCM 或服务器订阅。正式公网推送是否需要，再按送达需求和后台成本验证。

WorkManager 的周期执行受约束和系统优化影响，不是精确定时器；断网和休眠可能推迟甚至跳过某次运行。三小时是检查目标，不能宣传准时或实时送达。[Android WorkManager 周期任务文档，2026-09-30 核验](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work)

规划实现要求：

- 唯一周期任务，网络连接约束、请求合并与有上限退避。手动复查和后台检查共用领域事件引擎，不能拥有两套阈值或基线规则。静默期间可更新检查记录，发送另行受限。
- 持久化 `planRevisionId`、订阅状态、可比较版本、候选事件/确认次数、最后检查成功时间及错误、最后投递时间、已通知状态、待合并事件与全局通知预算。一次失败不覆盖上次成功内容。
- 使用统一事务仓库（例如 Room）或经过验证的串行访问方案。不能让独立 Worker 与 ViewModel 同时读改写现有 `plans.json`；AtomicFile 防部分写入，并不解决两个写者丢更新。
- 幂等键包含计划修订、事件因素及影响时段/状态；源版本用于判断新证据，不让每个新周期自动产生一个新通知。发布前重新读订阅、渠道、静默、计划开始时间和预算。
- 投递记录与 Android 系统通知不是一个原子事务。预留投递记录、使用稳定通知 ID 和重试抑制，避免崩溃重试反复打扰；区分“请求发布”“系统可显示”“用户已查看”，不把 `notify()` 成功当成已读证明。
- 用户关闭、删除、改时间或全局停用后，撤销旧修订事件和对应通知；进程重启不得清空去重预算。跨时区和系统时钟回拨保守处理，不能靠换日期恢复额度。
- 本机服务离线时展示上次成功检查及当前未能更新，不发“天气恶化”，也不连发失败通知。离开同一 Wi-Fi 的可用性见[真机测试限制](device-testing.md)。

## 必须验收的场景

| 场景 | 预期 |
| --- | --- |
| 首次打开 / 拒绝权限 / 系统关闭渠道 | 不自动弹权限、不反复索取，基础功能可用，跟踪设置如实反映状态 |
| 首次保存、相同源版本重复检查、无变化 | 0 条通知 |
| 数值四舍五入后相同、仅边界抖动、变化后恢复 | 不产生无意义提醒；未确认候选撤销 |
| 总雨量不变但雨小时移位 | App 内正确显示小时变化；符合触发和确认门槛后才通知 |
| 五个计划同时变化 / 跨午夜 / 时区改变 | 合并处理，全 App 滚动 24 小时最多一次，不因每计划或日历日重置而重复 |
| 静默中变化 / 早晨已恢复 / 活动已开始 | 静默不打扰；发送前重评，已恢复/过期不补发 |
| 缺值、旧缓存、口径变更、同快照重复抓取 | 显示真实信息状态，不计为新的天气确认或恶化 |
| 两个新周期确认，之后持续同方向 | 第一条合格摘要后不重复同一影响，除非产生新的有意义事件并再次通过预算 |
| 通知后恢复、反复变差变好 | 与上次通知状态比较并防抖，仍受全局限频 |
| 前台和 Worker 同时检查/改名/删除 | 不丢计划、不重写基线、不发布已撤销计划的通知 |
| 进程退出、设备重启、权限撤回、系统强行停止后再打开 | 不丢去重记录；恢复后不集中补发。各设备后台行为实测，不假设强行停止后仍能工作 |
| Doze、断 Wi-Fi、PC 休眠、网关返回错误 | 允许延迟、保留旧数据并退避，无失败通知轰炸，恢复后只发送仍有效事件 |
| 锁屏与通知点击、已删除计划 | 隐藏敏感行程；正确进入变化详情，删除场景有恢复路径 |

领域测试验证事件、预算和持久化；仪器/真机测试验证权限、渠道、后台和跳转。模拟时间可验证静默与限频，不替代真实待机和耗电观察。以上均为后续实现验收要求，本轮没有声称通过。
