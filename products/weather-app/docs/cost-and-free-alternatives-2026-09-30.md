# 持续成本、免费商用替代与个人开发者可行性

核验日期：2026-09-30。阶段：研究与小型 Docker 实验，不是采购或生产部署。用户已确认：面向欧美评估成本；优先现实可用的免费商用来源；不把超大参数模型部署作为个人开发者方案。广告、订阅、买断仍在重新评估，本报告不将订阅建议改写为已确认决定。

## 1. 结论

首期并不需要采购闭源 AI，也不需要自己训练或运行全球天气模型。应把气象机构已经算好的预报、我们自己的决策规则、可选的文字生成分开。闭源模型不是持续成本必然很高的充分条件，开源也不是总成本低的保证；应比较同样功能、流量、质量和维护时间下的总成本。

最值得验证的三条路线：

1. **最低运维路线：MET Norway / 美国 NWS 官方 JSON + 缓存 + 本地规则。** 数据服务可以免费商用，但字段、时效、国家和来源数量不足以完整兑现原设计。
2. **完整度更高的低成本候选：Open-Meteo 开源查询服务 + 其 AWS 开放数据 + 小范围缓存。** 这不同于免费托管 API：自托管允许商用，可按需取数据，不必运行天气模型或下载全世界全部文件。需要承担主机、缓存和故障处理。
3. **付费托管作为成本对照：购买现成聚合 API。** 支付的是数据加工、交付和运维服务，不必然是闭源模型许可。如果自托管维护更贵，低额固定套餐仍可能划算；尚未核实可靠报价，不写死金额。

一个月周趋势不是普通小语言模型能补出来的。可用真实次季节数据时才提供；来源、基准或质量不达标就暂不开放。

**本轮新增实证**：修正临时缓存目录权限后，官方 Docker 查询服务成功从开放数据返回伦敦的三模型短期数据与 EC46 周距平，无付费 API、无 GPU。短期查询为 3 模型 × 4 变量 × 48 小时且无空值；周趋势 7 个标签中 6 个有效。冷请求约 42 / 5 秒，原样重查约 7 / 6 毫秒；结束时容器内存快照约 526 MiB。这只证明单地点小查询可行，不是生产资源下限、并发能力或气象准确度结果。[完整实验与配置](../experiments/free-sources.md)

## 2. “模型”与“收费”分开看

| 层次 | 本产品需要做什么 | 是否需要自己推理 / 训练 | 成本来源 |
| --- | --- | --- | --- |
| IFS、GFS、ICON、AIFS、EC46 等气象系统 | 读取已产生的数值或统计产品 | 不需要 | 数据许可、交付、解码、缓存和质量检查 |
| 活动窗口、地点比较、计划变化 | 时间与单位标准化、按用户阈值筛选、保存和比较快照 | 确定性规则；普通 CPU 或手机即可 | 应用开发、少量计算和存储 |
| 自然语言摘要 / 偏好解析 | 可选地把结构化结果改写或把文字转成条件 | 首期不需要；将来只评估小模型 | 权重分发、运行内存、延迟、电量或服务器资源 |

现有[预报方法](forecast-method.md)已经按规则引擎设计，没有必须调用 LLM 的步骤。诸如“周六上午风较小，但两个来源对降雨有分歧”，完全可以由模板生成。无须引入向量数据库、AI Agent 或聊天后端。

ECMWF 当前开放子集包含 IFS 和 AIFS 的已计算结果，许可允许署名后商用；公开格点、时步与完整业务产品不同。使用 AIFS 的结果不意味着我们要购买 GPU 来运行 AIFS。[官方开放数据](https://www.ecmwf.int/en/forecasts/datasets/open-data)

## 3. 哪些地方会持续花钱

| 成本项目 | 是否不可避免地向第三方持续付费 | 免费商用 / 低成本替代 | 剩余限制 |
| --- | --- | --- | --- |
| 基础天气 | 否 | MET Norway、NWS；或自托管开放数据查询 | 无 SLA、地区/字段限制；自行缓存和适配 |
| 多模型与 7–16 天详情 | 否，但接入和运维有成本 | Open-Meteo 自托管；直接接入 ECMWF / NOAA / DWD 作为后续路线 | 核查原生时步、缺值、独立来源，不能仅看 API 输出为 hourly |
| 第 3–6 周趋势 | 不一定 | EC46 开放数据查询候选；GEFS / CPC 研究对照 | 数据交付、统计基准和质量验证；不能用 LLM 代替 |
| 官方预警 | 美国有免费官方入口；欧洲按国家核实 | NWS alerts；各国官方 CAP/其他授权源 | NWS 不覆盖整个欧洲；未落实前不能承诺欧美统一预警 |
| 城市搜索 | 否 | GeoNames 城市数据导入本地索引 | 适合城市/城镇，不等价于完整街道地址、步道 POI |
| 地图 | 首期可避免 | 地点列表和比较卡片；后续单独评估地图服务 | 开源渲染器不附赠底图托管；不能滥用 OSM 公共服务 |
| 条件解释 / 推荐 | 否 | 规则、格式化和翻译模板 | 模板应覆盖未知、缺值、冲突，不虚构概率 |
| 变化提醒推送 | FCM 通道当前免费 | FCM + 自己的定时比较作业 | 后台抓取、存储、队列与重试仍有成本，免费通道不是免费后端 |
| 收藏 / 草稿 | 否 | Android 本地数据库 | 跨设备同步延后 |
| 主机、缓存、带宽、备份 | 商业运营应预留持续预算 | 轻量单服务；有限云免费额度只能作为早期缓冲 | 自有电脑也有电力、网络和可靠性成本；不能假定免费额度永久足够 |
| 监控 / 日志 | 不必须订阅 SaaS | 自有结构化日志、限量保留、基础探活 | 值守和故障处理需要时间 |
| 广告 / 会员系统 | 不需要付费订阅管理 SaaS 才能做 | 官方 SDK / 商店接口 + 最小权益服务 | 对账、隐私管理、商店扣费与税费另计；SDK 免费不是零业务成本 |
| 上架和分发 | 与日常数据账单不同 | Android 优先 | Google Play 注册当前 $25 一次性，不能算成每月模型费；iOS 仍延后 |

来源：[GeoNames 数据许可与下载](https://www.geonames.org/about.html)、[FCM 定价](https://firebase.google.com/pricing)、[Google Play 注册](https://support.google.com/googleplay/android-developer/answer/6112435)。上架交易费按实际渠道和地区核算，本次不假定统一费率。

公开 Nominatim 限整个应用最多 1 请求/秒，并禁止用其公共接口实现自动补全，不作为首期搜索后端。[使用政策](https://operations.osmfoundation.org/policies/nominatim/)

## 4. 免费天气来源的实际可用性

### 4.1 MET Norway：能商用，但不是完整替代

官网明确允许商业用途；数据通常为 CC BY 4.0 / NLOD 2.0，须署名。接口要求标识应用、按缓存头取数，整个应用超过 20 请求/秒需特别约定，不提供 SLA。首期应通过自有缓存代理，不把每个客户端的反复刷新直接转发到上游。[官网](https://api.met.no/)、[许可](https://api.met.no/doc/License)、[使用条款](https://api.met.no/doc/TermsOfService)

2026-09-30 Docker 实测伦敦、柏林 `complete` 接口均 HTTP 200，各 92 行，覆盖至 10 月 9 日 12:00 UTC。其中相邻时间戳有 64 个一小时间隔、27 个六小时间隔；一小时降水量各 64 行；两个样本都未返回阵风字段。完整证据见[实验](../experiments/free-sources.md)。

因此可支撑基础天气参考，不能原样满足当前要求“至少两个来源 + 全部条件含阵风 + 原生小时”的活动推荐。要么补足来源，要么另行设计并明确展示较少条件的降级功能，不能把缺失阵风当 0。还要查明上游模型：不同 API 品牌可能实际都使用 ECMWF，不能重复计为两个独立模型。

### 4.2 NWS：美国优先路线更直接

NWS API 官方明确免费、可用于任何目的，提供预报、观测和 alerts；有限流但未公开固定上限。本轮纽约 points 和 hourly 均返回 200，得到 156 个小时区间。hourly 样本没有雨量和阵风，相关字段需要另查 grid data，不能认为 hourly 一个端点已完成接入。[官方接口文档](https://www.weather.gov/documentation/services-web-api)

美国点位与预警接入更集中，是技术成本角度的候选首发市场；不是已证实的获客优势，也不因此自动更改英国研究样本的决定。

### 4.3 Open-Meteo：三种访问方式不要混淆

| 方式 | 商用状态 | 我们承担什么 |
| --- | --- | --- |
| 官方免费托管 API | 当前限非商业评估 | 可用于研究，不能用广告 App 流量长期绕过商业套餐 |
| 官方商业托管 API | 付费商业许可；季节/集合等当前需 Professional 或以上 | 套餐费用、自有缓存、字段验证；本次未核得可靠固定月价 |
| 开源服务 + AWS 开放数据 | 官方明确自托管可商用；代码 AGPL-3.0、数据 CC BY 4.0 | 自有主机、运维和相应许可义务 |

托管套餐当前采用月度额度及固定月价；超过两周、多变量等请求可能折算多个计费单位。不能把一个 HTTP 请求直接算成一个计费单位。[套餐](https://open-meteo.com/en/pricing)

官方自托管文档列最低 8 GB 内存、推荐 16 GB，以及小中部署至少 100 GB 存储。支持从远程分块数据按需读取和本地缓存，首次访问可能慢。它运行的是天气查询服务，不是天气预测神经网络；无需 GPU。[自托管指南](https://github.com/open-meteo/open-meteo/blob/main/docs/getting-started.md)

AWS 数据库采用 CC BY 4.0，支持细粒度读取，发布方不保证完整性或连续供应。本轮目录查询看到了 `ecmwf_ec46/`、`ecmwf_ec46_ensemble_mean/`、`ecmwf_ec46_weekly/`，不能因静态 README 未列 EC46 就推断没有。[开放数据库](https://github.com/open-meteo/open-data)

自托管实验结果另见[实验记录](../experiments/free-sources.md)。目录存在、一个请求成功和生产持续可用分别是三种不同证据。官方资源建议不能被一次小请求的低内存读数替代。

采用 AGPL 服务时保留许可证、署名并履行适用源码提供义务；修改服务或组合其他代码之前审查边界。仅通过 API 使用它，不应未经分析就断言独立 Android 客户端也必须全部开源。若不接受相关义务，应改用其他实现或商业服务，不能去掉许可证。

### 4.4 直接原始数据与长期预报

- **ECMWF**：公开 IFS/AIFS 子集可以免费获取商用，完整目录开放不代表定制交付没有服务费。直接获取 EC46 的具体交付与费用仍需确认，不能把常规下载时效简单改成 46 天。[服务协议说明](https://www.ecmwf.int/en/forecasts/accessing-forecasts/service-agreements)
- **NOAA GEFS**：官方 v12 说明中的 00 UTC 延伸至 35 天，适合作为长期集合对照；但要核实当前分发文件确实覆盖第 17–35 天，并处理成员、基准和校准。本轮未下载完整 GRIB，不能认定已具备生产管道。[官方说明](https://www.emc.ncep.noaa.gov/emc/pages/numerical_forecast_systems/gefs.php)
- **美国 CPC**：提供第 3–4 周的区域温度/降水展望，可先提供官方入口。它是两周尺度的区域趋势，不是每个城市未来一个月的逐日天气；结构化接入尚未验证。[官方展望](https://www.cpc.ncep.noaa.gov/products/predictions/WK34/)
- **DWD**：有免注册开放数据服务器，但 GRIB 解码、字段语义、文件调度等仍由我们负责。本轮许可细则页面读取失败，具体产品授权待补核，不把“服务器开放”当作所有内容一概免条件。[官方入口说明](https://opendata.dwd.de/README.txt)

首期不建设全量全球 GRIB 管道。若以后直接接入，先限制国家、变量、预报周期与时间范围；HTTP Range 常能减少变量/时效下载，但不自动保证任意矩形区域都能在压缩 GRIB 内局部读取。

## 5. 真要加 AI，哪些小模型才值得试

首选仍是无模型模板。只有自然语言输入或摘要的任务测试证明收益，才进入小模型实验；不为了宣传“AI 天气”增加成本和幻觉。

| 候选 | 官方许可 / 规模 | 已核实的资源信息 | 适合的有限任务 |
| --- | --- | --- | --- |
| Qwen3-0.6B | Apache-2.0；0.6B | 官方 Q8_0 GGUF 文件约 639 MB | 短偏好转字段、简短改写；优先试验候选 |
| Qwen3-1.7B | Apache-2.0；1.7B | 官方 Q8_0 GGUF 文件约 1.83 GB | 0.6B 质量不足时的对照，不预设更大就值得 |
| SmolLM2-1.7B-Instruct | Apache-2.0；1.7B | 官方支持 CPU 示例，面向轻量文本任务 | 英文摘要/改写对照；不作为气象数值来源 |

来源：[Qwen 0.6B 官方文件](https://huggingface.co/Qwen/Qwen3-0.6B-GGUF/tree/main)、[Qwen 1.7B 官方文件](https://huggingface.co/Qwen/Qwen3-1.7B-GGUF/tree/main)、[SmolLM2 模型卡](https://huggingface.co/HuggingFaceTB/SmolLM2-1.7B-Instruct)。这是保守候选清单，不是最新模型排行榜，也没有做天气任务质量比较。

文件大小不等于运行内存。实际还有 KV cache、工作缓冲、上下文和并发。纯权重的 4-bit 理论量为参数数 × 0.5 字节：0.6B 约 0.30 GB、1.7B 约 0.85 GB；这不是已经下载的量化文件大小，更不是手机 RAM 要求。MoE 的“激活参数少”也不等于只需存储那部分权重。

实验建议：短上下文（先限定 1–2k token）、单并发、短输出；优先 CPU 验证，不先租 GPU。模型只生成结构化偏好或受约束的文字，时间、数值、单位、概率与未知状态必须由程序验证。失败回退到模板。Android 下载体积、峰值 RSS、耗电、发热和中低端机延迟均未测试，不能因电脑能运行就内置到所有用户手机。

本轮没有下载或运行语言模型，没有伪造 tokens/s、内存占用或准确率。也不采购大模型 API 或启动 GPU 服务。若日后考虑按量 API，小流量时可能比全天自托管更便宜，应用实际 token 数与同等质量实测比较，不能仅凭“闭源”判断成本必然高。

## 6. 成本账怎么做才有用

分别记录现金支出和个人时间：

`月现金成本 = 主机 + 存储/备份 + 流量 + 天气交付服务 + 可选 AI + 监控/消息等外部服务`

`经济成本 = 月现金成本 + 运维/适配小时 × 自己设定的时间价值`

`上游刷新量 ≈ 去重后的活跃网格/地点数 × 每日必要刷新次数 × 30`

付费聚合服务还需乘模型/变量/时间跨度等计费权重；自托管则记录冷读字节数、缓存命中、S3 请求、磁盘和 CPU。不能把 MAU 直接当成接口次数，也不能把所有用户的远期集合每天重复下载一遍。天气缓存与用户行程数据分开，避免隐私代价。

例如 500 个去重位置每天各刷新 4 次，基础量是每月 60,000 次更新；加入多模型与后台计划后的实际权重仍要测。这里只是算术示例，不是支持 500 个城市的容量测试。

现阶段不报一个伪精确的“每月 $5 包全部天气”数字。缓存代理与完整自托管查询服务的规格不同；免费数据并不自动把服务器账单降至零。采购前拿真实数据负载对比固定托管报价，超过预算时减少功能/范围，不用免费公共实例绕过限制。

## 7. 推荐决策与下一项验证

用户约束：个人开发者负担得起，不部署超大模型。规划建议：首期 AI 调用预算为 0，采用规则与模板；不采购独家闭源天气模型，不自训气象模型。

优先验证 Open-Meteo 按需自托管是否能提供原设计需要的短期多来源与 EC46 周统计；MET Norway / NWS 保留为基础天气或区域路线候选。供应商替换不应悄悄改变来源定义、时间步长或用户保存基线。

进入选型前还需：

1. 连续采样目标地区的缺值、更新时间和原生字段，核实周趋势的统计基准；一个请求成功不算通过。
2. 对同一组真实查询记录自托管冷/热延迟、内存、磁盘、流量，与正式商业套餐做成本比较。
3. 验证源故障和数据过期时的降级；不合格小时数据不运行原有窗口算法。
4. 明确首发国家预警来源和归属标注；用可交付功能回头验证用户是否愿意使用/付费。

若低成本方案能提供核心价值，广告、买断与订阅都应重新按实测经济性评估；不再以“天气必然有昂贵模型成本”为订阅的前提。技术便宜不证明用户愿意留下，会员也不能仅靠我们的服务器有账单来证明合理。
