# Android 内部版产品自检与整改顺序

日期：2026-09-30。审查基线：`8cbb6df`。本轮是用户要求的自检，交付问题证据、体验整改和通知规格，没有修改客户端、重打 APK 或宣称完成真机验收。

## 结论与用户选择理由

现版达到了真实数据链路样机的程度，没有达到可以持续使用的天气 App 体验。之前侧重构建、缓存和数据口径验证，没有落实设计中的天气视觉、日常查看和主动跟踪。用户指出的“全是文字”是核心体验缺陷，不能靠工程测试通过或“内部版”来解释为已完成。

用户选择我们的假设仍应是：**一眼看懂天气，方便选定出行时间，保存后有人替自己留意变化。** 现版三项均不完整；如果仍要用户阅读十二张数字卡、手动刷新、自己判断差异，用户缺少从免费竞品迁移的理由。无需先增加 AI、更多远期天数或大地图来解决这一问题。

## 审查范围与证据强度

- 已检查：Android 页面、状态管理、计划存储与比较、Manifest/依赖、服务端字段与评价规则，以及需求、交互、路线图之间的差异。
- 已执行：现有 16 项后端测试全部通过；使用现有已编译 Android Kotlin 函数，在 Docker JVM 中复现两项变化比较缺陷，见下文。
- 未执行：手机触控、TalkBack、200% 字体、截图验收、耗电、Doze、通知送达和离线生命周期测试。代码能证明功能缺失，不能替代这些体验验证。
- 优先级：本报告“阻断”指下一版体验验收前必须处理；“随后”指紧随其后的完善项。它们不代表完整产品 P0 已经完成。

## 问题清单

| 编号 / 顺序 | 发现与用户影响 | 证据与整改验收 |
| --- | --- | --- |
| A01 阻断 | 应用内没有天气图标、天气概况、趋势图；底部导航用文本字符充当图标。品牌大标题和技术说明占据首屏，用户难以扫读天气。 | [MainActivity](../app/android/app/src/main/java/app/dayward/MainActivity.kt) 的 `Dayward`、`Weather`、`Assessment`。实现独立矢量天气图标、标准导航图标、当前预测概况和小时趋势；正常状态首屏直接回答“哪里、何时、天气怎样”。启动器资源确实存在，但不能代替应用内天气视觉。手机启动器是否显示异常尚未核验。 |
| A02 阻断 | 当前数据仅四类数值，无法可靠区分晴、多云、雾、雪等天气，图标不能凭温度和零雨量推断。 | [provider](../service/provider.mjs) 的查询和标准化。验证每个源的天气代码、昼夜字段、采样定义和缺值；映射后才能显示相应图标，未知显示未知。不要将两个源混成虚构的统一天气条件。 |
| A03 阻断 | 保存后只能手动检查，无后台任务、通知权限、通知渠道、逐计划订阅和停用入口。“替我留意”尚未实现。 | [WeatherModel](../app/android/app/src/main/java/app/dayward/WeatherModel.kt)、[Manifest](../app/android/app/src/main/AndroidManifest.xml)、[依赖](../app/android/app/build.gradle.kts)。F09 提前至下一内部质量版核心工作，实施条件见[通知规格](notifications.md)。 |
| A04 阻断 | 比较只看整段极值/累计值，忽略已有小时序列；同时对 Double 做精确不等判断。会漏掉时段移动，也会把无意义抖动列成变化。直接复用会产生漏报和打扰。 | [PlanLogic](../app/android/app/src/main/java/app/dayward/PlanLogic.kt) 的 `comparePlans`，两个已复现实例见下文。改为结构化小时事件、偏好阈值与显著变化筛选；显示精度相同不应生成无意义差异。 |
| A05 阻断 | 所有真实窗口因起报、原生步长和预警覆盖未知而保持 `insufficient`。直接监听 `fits → outside` 无法给这版真实数据产生有效通知；新的抓取也不等于新的起报周期。 | [provider](../service/provider.mjs)、[domain](../service/domain.mjs)。保留严格推荐门槛，分开“数据可比较”“计划偏好结论”“预警可用性”。先解决来源版本追溯，不能靠放宽标签把数据不足变成适宜。 |
| A06 阻断 | `load()` 请求前清空已有天气；刷新失败后原来可看的数据消失。天气没有磁盘缓存，重启断网只能看已存计划基线。 | [WeatherModel](../app/android/app/src/main/java/app/dayward/WeatherModel.kt)、[Repository](../app/android/app/src/main/java/app/dayward/Repository.kt)。同地点刷新保留最后成功快照，标注过期；不同地点不能错用上一城天气。失败提供局部重试。 |
| A07 阻断 | 首次只取城市目录，需再点“Load collected forecast”；没有持久保存和恢复上次地点。开发设置占据主导航。 | `WeatherModel.init`、`Weather`、`Setup`。有缓存先显示，无缓存自动加载默认/上次地点；设置移至顶栏，LAN 配置放内部调试区。六城能力仍需如实标注，不能伪装全球搜索。 |
| A08 阻断 | 选时段用最多 48 项下拉菜单，天气却只展示前 12 小时，用户很难查看所选明日时段的逐时细节。天气查看与填写计划混杂在同一长页。 | `Weather` 的 `take(48)` 和 `take(12)`。天气、规划、已保存三项职责分开；日期条、连续小时轴、时长选择联动，同一数据覆盖范围内能看完再保存。 |
| A09 阻断 | 保存成功后还可以连续保存完全相同的计划，很快占满五个活跃名额；无重命名、修改或归档。过往和未来计划混排。 | `WeatherModel.save`、`Plans`。保存幂等，成功后“查看计划”；活动与历史分组，改时间/偏好建立修订，改名不丢基线。删除要撤销后续跟踪。 |
| A10 随后 | 变化检查仅存内存，退出后丢失；缺少最后检查时间、失败状态、上次已通知事件。直接增加 Worker 还可能与前台 JSON 写入竞争。 | `checks` 内存 Map、`PlanStore`。引入统一持久化仓库和事务/串行写入，分别保存原始基线、最新检查及投递记录；失败不覆盖成功数据。 |
| A11 随后 | 数据新鲜度来自请求时返回的状态，没有随驻留/恢复前台重新计算；切页共享外层滚动位置；全局消息可能残留在另一任务页面。 | `Dayward` 外层滚动容器、`Weather` 时间读取、`WeatherModel.message`。每页独立滚动与错误状态，前台恢复重算过期/计划是否已开始，必要时刷新。此项为代码审查发现，生命周期体感尚未实测。 |
| A12 随后 | 固定浅色、英文硬编码、固定公制和地区格式；主要信息大量用小字。面向美国用户缺少 °F/mph，辅助功能尚未验收。 | `lightColorScheme`、`Locale.UK/US`、`bodySmall`。实现单位偏好、字符串资源、深色；图标配语义、图表有文本入口，200% 字体与 TalkBack 真机验收。首发英文不等于本轮扩展所有语言。 |
| A13 随后 | 计划文件损坏时保留原文件并禁止写入是正确的，但没有用户可操作的恢复路径；页面直接读取 JSON 字段，异常结构存在渲染失败风险。 | `PlanCodec`、`Repository`、页面 `getJSONObject`。网络解析边界验证 DTO，错误进入可恢复 UI；存储损坏提供保留副本后的明确恢复操作，不自动清空。 |
| A14 发布/持续提醒前阻断 | 当前后端是本机 Docker + 局域网。PC 休眠、手机离开 Wi-Fi、Windows 转发未配置都会使检查失败；后台通知不能据此承诺全天候服务。 | [真机测试准备](device-testing.md)。局域网先测试交互与机制；后台失败只显示检查状态并退避。公网服务的可用性单独验证，不因本次自检启动部署。 |

现有值得保留的基础：真实数据与模拟数据分开；未知起报不补造；预警未知不写成无预警；原始保存基线不被复查覆盖；AtomicFile 写入和数据损坏保护；服务端缓存失败不替换旧快照。这些是可靠性基础，不能替代可读、好用的前台。

## 已复现的比较缺陷

[诊断程序](../experiments/ProductAuditProbe.java) 直接调用当前已编译的 `PlanLogicKt.comparePlans`，没有在 Java 重写算法。输入是构造的诊断数据，绝非真实天气。运行于无网络 Docker JVM，读取本地构建产物与 Gradle 缓存；源文件在审查基线之后未修改。

| 输入 | 实际输出 | 应整改为 |
| --- | --- | --- |
| 两小时雨量 `[1, 0] → [0, 1] mm`，总量、极值、状态相同 | `No change in the displayed window metrics since saving.` | App 内标出雨影响的小时后移；是否通知再经过订阅、版本和显著性规则，不能直接把汇总不变当作时段不变。 |
| 窗口累计雨量 `0.11 → 0.14 mm` | `GFS · total rain (mm): 0.1 → 0.1` | 过滤无意义展示差异，不能作为主动提醒理由。 |

诊断程序输出当前行为，不把缺陷写成必须永久保留的测试。修复时需为正确的事件语义补正式回归测试。

## 下一版页面整改

页面详细规格仍由[体验设计](experience.md)维护；本节规定整改交付重点。

1. **天气**：地点/设置顶栏 → 当前预测天气图标、温度、简短状态 → 当地时间和取得时间 → 温度曲线、雨量柱与风/阵风小时视图 → 选中时段的参考摘要。来源、分歧可展开；严重预警若实际接通则显著展示。没有合格自动建议时，主操作是手动选时间，不能让整页只剩警告。
2. **规划**：选日期、开始时间、持续时长和偏好；所选时间在图上高亮；先看主要影响，再展开两个模型的证据。超出真实覆盖的日期不可假装可用。保存后进入计划详情，不让用户重复保存占名额。
3. **已保存**：下一次活动优先，卡片直接列时间、地点、当前变化摘要、上次检查与跟踪状态；详情对照保存时/最新小时走势。改名、调整计划、停提醒、归档和删除可发现。
4. **图标系统**：晴/夜晴、少云/夜间少云、多云、雨、雪、雷雨、雾、未知等由已核验代码映射；风、雨量、时间、收藏、通知用功能图标。图标与文字互补，不能只靠颜色；优先矢量资源，统一线条、尺寸、明暗主题，不用 emoji 充当跨设备组件。
5. **错误与加载**：首次加载占位，同地点刷新旧数据不闪空；离线、部分变量缺失、全部失败分别处理；开发者术语放详情，关键来源限制仍在相关位置可见。
