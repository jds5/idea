# 技术与平台计划

更新日期：2026-09-23。状态：路线建议；没有经过真机验证。

## 1. macOS 与硬件策略

最低支持版本暂定 **macOS 15**，首期架构暂定 **Apple Silicon（arm64）**。理由是控制首款系统工具的兼容与设备测试规模，不是 Core Audio taps 只能在这些平台运行。Intel 和 macOS 14 暂不承诺，M0 结合实际目标用户需求重新评估。

Apple 的 [Core Audio taps 示例](https://developer.apple.com/documentation/coreaudio/capturing-system-audio-with-core-audio-taps)注明示例需要 macOS 14.2 或更高版本，并说明捕获指定进程、tap 静音行为、聚合设备及系统音频授权。能捕获音频不代表完整音量控制、重定向、故障恢复和沙盒分发已经成立。

按 2026-09-23 核验的 [Apple 系统版本页](https://support.apple.com/en-us/109033)，当前列出的正式系统包括 macOS 15、26 和 27。首期测试以这三代为范围，执行时重新核验并记录实际小版本与 build，不能只写“最新系统通过”。

| 环境 | 首期计划 |
| --- | --- |
| macOS 15 / Apple Silicon | 兼容下限，单独验证权限、基本 UI、音频与恢复；最低实际小版本在 M0 冻结 |
| macOS 26 / Apple Silicon | 完整功能和设备回归 |
| macOS 27 / Apple Silicon | 当前新系统适配，完整功能与视觉回归 |
| macOS 14、Intel | 调研需求与成本，未验证前不宣称支持 |
| 系统 Beta | 兼容预研，不作为正式支持或唯一测试环境 |

使用执行时可获得的稳定 Xcode 和 SDK，锁定版本写入工程 README / CI。新版 API 使用 availability 检查，并保证最低版本有等价核心流程。

## 2. 技术栈与模块

优先 Swift + SwiftUI + 必要的 AppKit。音频数据路径使用 Core Audio；需要时在实时部分采用 C / C++，不先引入跨平台 UI 或大型框架。

```text
主窗口 / 菜单栏
        ↓ 用户意图                 ↑ 真实状态
配置协调器（单一串行控制入口） ← 系统 / 设备 / 应用事件
        ↓ 执行计划
AudioBackend（能力查询、控制、观察、释放）
        ↓
Core Audio taps / 处理流 / 设备输出

配置存储 ↔ 配置协调器       诊断只记录状态与耗时
```

| 模块 | 责任 |
| --- | --- |
| AppUI | 展示、键盘与无障碍、将操作转为意图；不直接调用底层改路由 |
| ProfileDomain | 配置校验、差异、接管与释放计划、切换状态机；可用 fake backend 测试 |
| ProfileStore | 版本化持久化、原子写入、备份与迁移 |
| AudioBackend | 枚举进程和设备、增益 / 静音 / 路由、读回、能力限制、资源回收 |
| SystemObserver | 应用生命周期、设备热插拔、默认设备变化、休眠唤醒、权限变化 |
| Diagnostics | 结构化错误、操作耗时和资源信息；用户主动导出，默认无音频内容 |

模块先作为清晰代码边界，不要求一开始拆成多个独立包或服务。是否使用独立音频进程或 XPC，由故障隔离与沙盒实验结果决定。

## 3. 首选音频路线与验证顺序

1. 验证指定进程 tap 的捕获，以及 muted / mutedWhenTapped 等可用行为；实际符号和可用性以所用 SDK 为准。
2. 将目标音频送入可控处理路径，应用增益和静音，再输出到所选设备；确认原路径没有重复播放。
3. 建立两个应用、两个输出的并行路径，覆盖 44.1 / 48 kHz 与独立设备时钟；采样转换、缓冲和漂移处理不能假定由 API 自动解决。
4. 排除自身输出被再次捕获，验证辅助进程的归属，检查浏览器、Electron 和会议应用。
5. 验证进程退出、权限撤回、设备拔出、休眠唤醒、强制退出后恢复；清理自己创建的资源，不动其他音频工具的对象。
6. 最后接入配置协调器，验证完整场景切换和规则释放。

系统没有在本计划中被假定存在一个可直接设置所有第三方应用音量的通用滑杆 API；重新处理音频的成本、时延和兼容性必须测量。

ScreenCaptureKit 或其他捕获方式只作为实验候选，不把“拿到音频”视为已解决路由。若首选路线不能达标，先给出实测证据和调整方案，再决定是否引入驱动或 helper；首期不默认安装内核扩展、不要求降低系统安全级别。

## 4. 实时与并发约束

- 数据回调不访问 UI，不进行文件 / 网络 I/O、阻塞锁、日志格式化或不可控分配。
- 控制线程构建新参数与处理资源，通过有界且线程安全的机制提交；音频回调只消费准备好的数据。
- 设备监听和 UI 命令汇入单一协调器。用 transitionID 与 profile revision 丢弃过期事件。
- 资源释放与回调生命周期有明确顺序，不能一边销毁设备一边访问旧缓冲。
- 滑杆命令合并，避免每个 UI 事件都重建音频流。UI 只订阅必要状态，避免每个音频 buffer 都触发界面刷新。

## 5. 权限与本地数据

基于实际实现配置 `NSAudioCaptureUsageDescription`，向用户解释“用于分别控制应用音量与输出，音频在本机处理”。系统可能把此能力称为音频录制 / 捕获权限；文案不能否认底层访问音频的事实。

默认不录音、不转写、不上传音频；也不把麦克风、屏幕录制、辅助功能权限当作一揽子前提。每项额外权限必须对应实际能力并经过验证。切换系统默认输入不等于需要捕获麦克风内容。

配置包含应用与设备信息，按本地用户数据处理。诊断导出须预览或说明字段，脱敏设备标识；不要在常规日志写入完整音频、令牌或用户文件路径。

## 6. 沙盒与分发决策

M0 使用相同最小音频闭环验证两种构建配置：App Sandbox 开启，以及 Developer ID 直接分发所需的运行环境。记录 entitlement、签名、权限弹窗和各项能力的实际结果；一次本地成功不能等同商店审批。

Apple [审核指南](https://developer.apple.com/app-store/review/guidelines/)要求 Mac App Store 应用遵守沙盒、自包含安装等规则，并限制抄袭及低差异重复应用。因此：

- 存在同类产品不代表品类被独占，也不保证本产品可过审。
- 独立品牌、可演示的配置流程和完整用途需在实际产品中成立。
- 若沙盒内能完成首期能力，保留 App Store 路线；若不能，记录原因后评估直接分发。不能只凭竞品直接销售推导其技术必然无法上架。
- 直接分发规划 Developer ID 签名、Hardened Runtime、[公证](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)及可验证安装。公证与 App Store 审核不同。

最终渠道在 M0 后写入决策记录。更新机制、试用和支付随渠道确定，发布准备阶段再实现；不在原型期引入许可服务器。

## 7. 当前环境限制

当前开发环境为 Windows，不能运行 Xcode 或验证 Core Audio。`ProfileDomain` 已有独立的 Linux 容器测试命令，见[开发与测试](development.md)；这只覆盖跨平台逻辑。后续必须提供可用 Mac、至少两种物理输出、稳定签名身份及可复现实验记录。当前没有 macOS 构建或音频测试成绩可报告。
